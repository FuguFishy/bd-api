## Relationships

- contacts.organisation_id -> organisations.id
- projects.organisation_id -> organisations.id
- projects.contact_id -> contacts.id
- activities.contact_id -> contacts.id
- activities.organisation_id -> organisations.id
- activities.project_id -> projects.id
- tasks.contact_id -> contacts.id
- tasks.organisation_id -> organisations.id
- tasks.project_id -> projects.id
- tasks.activity_id -> activities.id

## Rules

- Use UUID primary keys for the final application layer.
- organisations is the parent lookup table.
- contacts must belong to an organisation.
- projects must belong to an organisation.
- project contact_id is optional.
- organisation_name is retained for UI/display and import staging only.
- organisation_id is the source of truth for relationships.
- Keep unique constraints and indexes on common lookup fields.
- Keep activities as the source of truth for meeting logs.
- Keep entity_matches for ambiguous or AI-assisted matching only.
- Keep workflow_runs for automation logging.
- Keep weekly_targets for target tracking.

## Operational notes

- Import organisations first.
- Import contacts next.
- Import projects next.
- Backfill organisation_id from organisation_name where needed.
- Reapply NOT NULL constraints after import/backfill if a temporary nullable phase is used.
- Keep Notion/CSV imports as staging only; the database is the long-term system of record.
